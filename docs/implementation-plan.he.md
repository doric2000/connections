# תוכנית בניית הפלטפורמה מתכנון ועד בטא

מסמך עבודה מיום 5 באוקטובר 2026. התוכנית מבוססת על הגרסה האחרונה הכוללת פרופיל מקצועי, קורות חיים וצ׳אט לפני הצטרפות. היא בונה בכל פעם תהליך שאפשר להפעיל בין אנשים, ומוסיפה לו עומק. [מסמך הארכיטקטורה](./architecture.he.md) מפרט אחריות ונתונים; [המחקר](./research.he.md) מקשר למדריכים וללקחים.

## סדר העבודה והנחות התכנון

העבודה מחולקת לעשרה שלבים. גיוס בעלי פרויקטים ומשתתפים מתחיל בשלב הראשון וממשיך לאורך הפיתוח. בניית המובייל מתחילה אחרי שהזרימה באתר הוכיחה שימוש, תוך שמירת אותו API.

טווחי הזמן כאן הם הערכה שלי לצורך תכנון, עבור מפתח אחד שמכיר React ולומד חלק מ־Spring ו־SQL. יום עבודה פירושו יום ממוקד. אלה אינם נתוני מחקר או התחייבות; לאחר שלב הוכחת החיבורים נעדכן אותם. בשיחה הישנה הוערכו 22–30 ימים; אין מספיק ראיות כדי להבטיח שהטווח הזה יכסה את כל מקרי הקצה והלמידה.

| שלב | תוצאה מרכזית | טווח מוצע |
| --- | --- | --- |
| 1 הגדרת מוצר ופיילוט ידני | גבולות V1 ומשתמשים ראשונים | 2–3 ימים, וגיוס נמשך במקביל |
| 2 מסכים, מצבים והרשאות | תהליך ברור למשתמשים ולמפתח | 2–3 ימים |
| 3 הוכחת חיבורים טכניים | Auth, DB, CV ו־Realtime עובדים בסביבת בדיקה | 3–5 ימים |

| 6 פניות וקורות חיים | בעלים בודק פונה עם הרשאות נכונות | 3–4 ימים |

סכום העבודה הטכנית וההכנה הוא בקירוב 28–43 ימים; נשאיר מרווח לתקלות, למידה ושינוי בעקבות משתמשים. מסגרת תכנון שימושית היא כ־30–50 ימי עבודה לפני ובתחילת הבטא. בקצב חלקי הזמן הקלנדרי מתארך. עבודה שמתבררת כמיותרת תוסר, במקום למלא את הטווח.

## שלב 1 הגדרת מוצר ופיילוט ידני

ננסח מסמך דרישות קצר סביב שני סוגי פעולות: אדם מפרסם פרויקט ותחומים פתוחים; אדם אחר מגלה, בודק, מדבר ומחליט להצטרף. נכתוב דוגמאות של אחריות משמעותית, למשל אבטחה, UI/UX וסושיאל ב־PlanLi. כל סעיף ב־V1 יקבל משתמש, צורך ותוצאה.

נשלים את ההחלטות הפתוחות ב־[יומן ההחלטות](./decisions.he.md), בעיקר CV, כללי שיתוף, הצטרפות, עזיבה וסוגי פרויקטים מותרים. שאלות של זכויות בתוצרים ותנאים דורשות ניסוח מתאים לפני השקה; מסמך זה אינו קובע את התוצאה המשפטית שלהן.

במקביל נערוך שיחות עם בעלי פרויקטים ועם אנשים שרוצים לצבור ניסיון. יעד עבודה מוצע, לא סף מחקרי: 5–8 בעלי פרויקטים ו־8–12 משתתפים פוטנציאליים. נשאל על הפעם האחרונה שניסו למצוא עזרה או פרויקט, איפה חיפשו, מה נכשל, מה היה חסר, ומה נדרש כדי להסכים לעבוד עם אדם זר. ננסה לארגן כמה היכרויות אמיתיות ידנית, ברשות המשתתפים, כדי להבין את ההתנהגות לפני כתיבת כל המערכת.

תוצר: Product Brief, גבולות V1, רשימת הנחות ואנשים שמוכנים להשתתף בפיילוט. תנאי סיום: לפחות כמה פרויקטים קונקרטיים עם צורך ברור; אין הסתמכות רק על תשובות ״רעיון טוב״. ההמלצה להתחיל בקבוצה ממוקדת נשענת על ניסיון שהצטבר אצל מייסדי marketplaces; היעדים המספריים כאן הם הבחירה שלנו. [Sharetribe Strategy](https://www.sharetribe.com/academy/marketplace-strategy-principles/)

## שלב 2 מסכים, מצבים והרשאות

נשרטט wireframes פשוטים של גילוי, פרויקט, פרופיל, יצירת פרויקט, תחום פתוח, פנייה, מסך הפונים, שיחה, הזמנה, צוות ותרומה. כלי כגון Figma יכול לעזור, אך התוצר החשוב הוא בדיקה של התהליך עם משתמשים. אין צורך להשלים מערכת עיצוב שלמה לפני הבדיקה.

לכל מסך נגדיר happy path וגם טעינה, ריק, שגיאה, אין הרשאה, פנייה כפולה, פנייה שנמשכה ופרויקט שנסגר. נבדוק עברית, RTL, טלפון ומקלדת. נכתוב במפורש מה ציבורי ומה אישי.

נכין מטריצת הרשאות: אורח, משתמש, פונה, בעל פרויקט, משתתף שיחה, חבר צוות ומנהל. נשרטט את הישויות ואת מצבי עניין, הזמנה וחברות בנפרד. שם זהה בממשק לא יסתיר שתי פעולות שונות בקוד.

תוצר: Screen Map, ERD ראשוני, State Diagram, Permission Matrix וקריטריוני קבלה. תנאי סיום: משתמש יכול להסביר מתי הוא רק מתעניין, מתי הוא משוחח ומתי הוא מצטרף. [Next.js Authentication](https://nextjs.org/docs/app/guides/authentication)

## שלב 3 הוכחת החיבורים הטכניים

נבנה ארבעה ניסויים קטנים עם שלוש זהויות: בעל פרויקט, פונה ואדם שלישי שאינו מורשה. המטרה היא להסיר אי־ודאות בתשתית לפני שנשקיע במסכים רבים.

| ניסוי | מה מוכיחים | כישלון שאסור להסתיר |
| --- | --- | --- |
| התחברות | Google או דוא״ל → session באתר → JWT מאומת ב־Spring | אסימון שפג, issuer אחר או אלגוריתם לא מתאים |
| מסד ופריסה | Java מתקשר ל־Supabase דרך JDBC מסביבת Cloud Run לבדיקה | IPv4/IPv6, SSL, pool או prepared statements לא מתאימים |
| קורות חיים | העלאה פרטית ושיתוף עם בעלים מורשה | אדם שלישי או פרופיל ציבורי מורידים CV |
| שיחה | הודעה נשמרת, מגיע אירוע פרטי, ורענון משחזר היסטוריה | ניתוק, אירוע כפול, חסימה עם socket פתוח או הודעה כפולה |

נבצע פריסת בדיקה קטנה בשלב הזה, לפני בניית שאר המוצר. היא אינה השקה לציבור. תוצר: קוד הוכחה ממוקד, תוצאות הניסויים ובחירות חיבור מתועדות. תנאי סיום: הכשלים מטופלים או שהארכיטקטורה עודכנה באופן מפורש.

מדריכים: [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/nextjs), [Spring JWT](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html), [Database Connections](https://supabase.com/docs/guides/database/connecting-to-postgres), [Storage Permissions](https://supabase.com/docs/guides/storage/security/access-control), [Realtime](https://supabase.com/docs/guides/realtime/subscribing-to-database-changes), [Cloud Run Java](https://docs.cloud.google.com/run/docs/quickstarts/build-and-deploy/deploy-java-service).

## שלב 4 בסיס המאגר וסביבות

נקים apps/web, backend/api וחבילות משותפות נחוצות. לא נייצר אפליקציית mobile ריקה רק כדי למלא תיקייה. ננעל כלים, נכתוב README ו־env.example ללא סודות, ונגדיר הרצה מקומית ותצורת staging.

נגדיר migrations עם Flyway, תפקיד מסד ל־runtime ותפקיד לשינויי סכמות. CI יפעיל lint, typecheck, בדיקות רלוונטיות ובנייה. OpenAPI ייבדק, ויצירת לקוח TypeScript תהיה פעולה חוזרת שלא דורשת שינוי ידני של טיפוסים.

נייצר נתוני פיתוח סינתטיים עם שני פרויקטים ושלושה משתמשים. נתוני אמת יתווספו רק לפיילוט שמוסכם עם בעליהם. תוצר: מאגר שמפתח יכול להרים מהוראות קצרות. תנאי סיום: checkout נקי מגיע לאותה מערכת מקומית בלי עריכה ידנית של המסד.

מדריכים: [Next.js Installation](https://nextjs.org/docs/app/getting-started/installation), [Spring REST](https://spring.io/guides/gs/rest-service/), [Local Supabase](https://supabase.com/docs/guides/local-development), [Flyway ב־Spring](https://docs.spring.io/spring-boot/how-to/data-initialization.html), [OpenAPI Generator](https://openapi-generator.tech/docs/generators/typescript-fetch/).

## שלב 5 פרופילים וקטלוג פרויקטים

נבנה פרוסה מלאה: משתמש מתחבר, משלים פרופיל, יוצר פרויקט ותחום פתוח, מפרסם אותו, ומשתמש אחר מוצא אותו. בכל חלק ניישם מסד, endpoint, הרשאה, מסך וקריטריון קבלה יחד. אחרי שזה עובד נוסיף עריכה, pause, archive, חיפוש ומסננים.

הפרופיל מפריד בין מה שהאדם יודע לתרום לבין מה שהוא רוצה ללמוד. תחום פתוח מאפשר Focused, Ongoing ו־Flexible. העמוד הציבורי כולל תיאור, שלב, טכנולוגיות, צוות ותחומים פתוחים, עם metadata לשיתוף.

תוצר: קטלוג פרויקטים בר־שימוש ופרופילים בסיסיים. תנאי סיום: פרויקט טיוטה אינו ציבורי, אדם אחר אינו עורך אותו, חיפוש מחזיר נתונים אמיתיים עם pagination, והמסכים עובדים בעברית ובטלפון.

מדריך deployment של Next.js ישמש לקביעת rendering ו־cache. אנחנו בוחרים public pages לפי צורכי גילוי, ולא מוסיפים ORM נוסף ל־Next.js. [Next.js Self Hosting](https://nextjs.org/docs/app/guides/self-hosting)

## שלב 6 התעניינות וקורות חיים

נוסיף הבעת עניין עם הודעה ראשונית, דרישות פרופיל וצירוף חובה של קובץ קורות חיים. המשתמש יוכל לשמור כמה קבצים בהגדרות ולבחור אחד לכל פנייה; קישור GitHub הוא תוספת לבחירה. בעל הפרויקט יקבל את הקובץ שנבחר למועמדות המסוימת. הפונה יכול למשוך פנייה לפני פתיחת שיחה; הרשאות המסמך והיסטוריית הגישה לאחר משיכה יוגדרו בכללי המוצר לפני היישום.

נבדוק ניסיון פנייה עצמי, פנייה כפולה, תחום סגור, CV גדול מדי, MIME לא מתאים, הרשאה שנמשכה ושינוי מזהים ב־URL. כל מידע שמופיע בפרופיל ציבורי נבדק גם בתשובת API ציבורית.

תוצר: בעל פרויקט מסוגל להבין מי מעוניין ולהחליט עם מי לדבר. תנאי סיום: אישור שהפנייה נבדקה אינו חברות בצוות, וה־CV מוגן גם אם פונים ישירות ל־API או ל־Storage. [Serving Private Files](https://supabase.com/docs/guides/storage/serving/downloads)

## שלב 7 צ׳אט והצטרפות בהסכמה

ניישם יצירת שיחה מהפנייה, הודעות, pagination, סדר, מצב קריאה והתאוששות מניתוק. הודעה שנשלחה שוב בגלל timeout תזוהה לפי client_message_id. נשמור את ההיסטוריה במסד ונשתמש ב־Realtime לעדכון הממשק.

נוסיף הזמנה לצוות, אישור של הצד השני, סירוב, ביטול ותפוגה. קבלת הזמנה תיצור חברות בצורה אטומית; רענון כפול או לחיצה כפולה לא ייצור חברים כפולים. נבדוק שהבעלים אינו יכול לאשר בשם הפונה, ושתחום שנסגר בין שליחה לקבלה מטופל לפי מדיניות מוגדרת.

תוצר: תהליך שלם בין שני אנשים, מגילוי ועד חברות. תנאי סיום: עברו גם התרחישים של אדם שלישי, חסימה באמצע שיחה, token refresh, ניתוק והזמנה שבוטלה. [Realtime Authorization](https://supabase.com/docs/guides/realtime/authorization)

## שלב 8 בטיחות, התראות וניסיון

נבנה report ו־block עם אכיפה בשרת, ממשק moderation קטן ומדיניות פרויקטים ברורה. דיווח נכנס לבירור ואינו גורר מחיקה אוטומטית. נבדוק הגבלת קצב בפניות ובהודעות בהתאם למסלול הכתיבה שנבחר.

נוסיף התראות פנימיות, outbox ודוא״ל מוצר עם retry. נגדיר SMTP להתחברות, נעבוד עם דומיין שולח מאומת ונבדוק קבלה אצל כתובות אמיתיות של צוות הבטא. אירועי analytics ימדדו מעבר בין שלבים; התוכן הפרטי לא יצורף לאירועים.

בהתאם להחלטת V1 נבנה תרומה בסיסית: המשתתף מתאר מה עשה, מצרף ראיות, בעל הפרויקט מאשר, ונוצר תיאור Project Experience שניתן לשתף. היקף המנגנון יהיה קטן וגלוי, בלי הבטחה לאימות תעסוקה.

תוצר: מערכת שניתן להפעיל בקהילה קטנה ולטפל בה. תנאי סיום: חסימה משפיעה בפועל, תקלה בדוא״ל לא מאבדת פעולה, והרשומות שאושרו מתארות עבודה אמיתית. [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [Resend Java](https://resend.com/docs/send-with-java), [Cloud Run Background Work](https://docs.cloud.google.com/run/docs/tips/general)

## שלב 9 בדיקות, התאוששות ופריסה

בדיקות הרשאות וכללי מוצר ילוו כל שלב; כאן נשלים את זרימת הבטא ואת היכולת להפעיל ולשחזר את השירות. לא נדחה אבטחת קורות חיים או צ׳אט לסוף.

| סוג בדיקה | מה נבדוק בפועל |
| --- | --- |
| JUnit | מעברי הזמנה, חברות, חסימה, סגירת תחום ושיתוף CV |
| Testcontainers PostgreSQL | עסקאות, אילוצים, migrations, אינדקסים ופניות מקבילות |
| Supabase מקומי | Auth, Storage ו־Realtime עם RLS והזהויות האמיתיות של השירות |
| Playwright | בעלים ופונה מגלים, משתפים CV, משוחחים ומאשרים הזמנה |
| staging | OAuth callbacks, SMTP, SSL, CORS, token refresh וחיבור למסד |
| שחזור | שחזור מסד והחזרת קובץ נבחר לפי מדיניות Storage נפרדת |

PostgreSQL רגיל ב־Testcontainers אינו הוכחה ל־RLS של Supabase או להתנהגות Auth/Storage. נבדוק את שכבות Supabase גם בסביבה שלהן. ב־E2E נבדוק התנהגות ותוצאה, לא פרטים פנימיים של רכיב. [Testcontainers Spring](https://testcontainers.com/guides/testing-spring-boot-rest-api-using-testcontainers/), [Playwright Best Practices](https://playwright.dev/docs/best-practices)

הפריסה תכלול secrets, service identities, migrations לפני revision חדש, בדיקות בריאות ו־rollback אפליקטיבי. שינויי מסד ייבנו בשיטת הרחבה ואז מעבר ורק אחר כך הסרה, משום שחזרה ל־image קודם אינה מבטלת אוטומטית migration. נגדיר התרעות תקלות וחיוב, מגבלות scaling ורישום requestId.

## שלב 10 בטא ולמידה

נפתח לקבוצה ממוקדת עם פרויקטים אמיתיים, למשל PlanLi ועוד כמה מוצרים שנבחרו בהסכמה. יעד התחלתי מוצע הוא 5–10 פרויקטים ו־20–40 משתתפים מתאימים. אלה מספרי תכנון שמאפשרים ללוות את האנשים, לא הבטחה לשוק.

נמדוד זמן לפנייה רלוונטית ראשונה, שיעור בעלי פרויקטים שמתחילים שיחה, זמן לתגובה, הזמנות, הצטרפות ותרומות שהתחילו או הסתיימו. הנתונים יופקו מתוך מצבי השרת; clicks משלימים את התמונה ואינם מחליפים אותה. נפריד בין חיבור שלא הצליח בגלל חוסר התאמה לבין תקלה או בלבול במוצר.

נסיים כל שבוע בעדכון הנחות ומשימות. נתחיל מובייל כאשר יש ראיות שהתהליכים באתר שימושיים ושהטלפון מוסיף ערך. Expo יקבל את אותו API client ומושגי המוצר; UI ישותף רק כשזה נוח למשתמש ולתחזוקה. [Expo Monorepos](https://docs.expo.dev/guides/monorepos/)

## שיטת העבודה בכל משימה

1. מגדירים תוצאה נראית ומי רשאי לבצע אותה.
2. מעדכנים סכמה או חוזה API במידת הצורך.
3. מיישמים שרת, מסך ומקרי שגיאה יחד.
4. בודקים הרשאות ותרחיש כשל שמשנה את התוצאה.
5. מריצים בסביבה מקומית ומציגים תוצאה ב־staging כשמתאים.
6. מתעדים החלטה ששינתה את התכנון ומתקדמים למשימה הבאה.

לכל יחידת עבודה יהיו צורך, גבולות, תוצאה וקריטריוני קבלה. נתחיל במשימות קטנות שמייצרות למידה. כלי AI יכולים לסייע בקוד ובבדיקה, אבל כל שינוי צריך להיות ברור לך: מה נשמר, מי מורשה לבצע אותו ומה קורה כשנכשל.

## יחידת העבודה הראשונה המוכנה

המשימה הטכנית הראשונה תהיה כניסה למערכת ו־GET /v1/me שמחזיר את המשתמש המאומת מתוך Spring. היא תחבר Next.js, Supabase Auth ו־Spring Security ותוכיח את הבסיס לשאר המוצר.

תוצרי הקבלה שלה: חשבון אחד נכנס; השרת מזהה sub נכון; בלי token מקבלים 401; token שגוי או מפרויקט אחר נדחה; UUID בגוף הבקשה אינו מאפשר התחזות; ורענון session מאפשר להמשיך. אחריה נמשיך ליצירת פרויקט ולתחום פתוח, כך שבתום הפרוסה הראשונה אדם שני יכול לצפות בעמוד אמיתי.
